# Release Markport HEAD

Use this workflow from the Markport repository root when the user authorizes a release of the latest committed revision. The release target is the HEAD SHA captured at the start. Do not create a release commit, silently include working-tree changes, or move an existing tag to make the release work. A separate request to change source or documentation can be completed first, then capture the new HEAD.

A release request authorizes automatic version selection, validation, tagging, pushing, and publication through final verification. Announce the selected version and rationale as a progress update, then continue without asking the user to choose a version or reconfirm publication. A request to edit this skill alone does not authorize an actual release.

1. Before running builds or tests, check release prerequisites. Inspect `AGENTS.md`, `git status --short --branch`, the HEAD SHA and tracking branch, recent commits/tags, `.github/workflows/release.yml`, and the relevant remote tag and GitHub Release state. Fetch when needed to establish the current remote state. Confirm that HEAD is the intended commit on the release branch and has not already been released. Leave unrelated untracked files, including `.codex/`, alone. If local changes look like intended release content, clarify whether they must be committed before fixing the target SHA. Check the required Go, Node.js, npm, Make, and Playwright tooling against `AGENTS.md`; note missing dependencies and install them using the repository's documented commands after the version is selected. Run `gh auth status -h github.com`, confirm `gh` can access the target repository, and use `git push --dry-run origin HEAD:refs/heads/<release-branch>` to check Git credentials, write access, and fast-forward eligibility. If a prerequisite fails, resolve it or request the needed authentication first; do not spend time on the full validation suite while publication is blocked.
2. Review the actual changes since the latest published stable version, using commit history and diffs, and select the next SemVer `vX.Y.Z` automatically. Use the highest-impact change: breaking changes require a major bump at 1.0 or later, new features a minor bump, and fixes or documentation/tooling-only changes a patch bump. Before 1.0, follow the repository's documented versioning convention; if none exists, use a minor bump for breaking changes or features and a patch bump otherwise, without automatically declaring 1.0. If the user supplied a version in the release request, use it instead of the automatic choice and briefly explain any difference. Check local and remote tags and Releases to ensure the version is unused and newer than the latest published stable version. If an automatically selected version is occupied, advance to the next unused version consistent with the bump; if an explicit version is occupied or invalid, report the conflict and request a replacement. Announce the selected version and brief rationale, then proceed immediately to validation and publication. Never reuse or force-update an existing tag without separate explicit authorization.
3. Run `make test`, `make lint`, and `make test-e2e` serially so their shared Vite build output cannot race. Run `make dist VERSION=<version>` afterward. Check that the six expected OS/architecture binaries exist, verify `dist/checksums_<version>.txt` from `dist/` using `sha256sum --check` (or the platform equivalent), and check the Linux amd64 artifact's `--version`. Stop on a real failure; diagnose and obtain a new release target if a code fix is required.
4. Recheck that HEAD still equals the captured SHA. Push the release branch with a normal fast-forward push, then create and push an annotated tag pointing to that SHA. Do not force-push. If SSH fails with `Permission denied (publickey)`, check `gh auth status -h github.com` and use HTTPS with the GitHub CLI credential helper when valid. If authentication expires after the preflight, stop and ask the user to renew it with `gh auth refresh -h github.com` or `gh auth login -h github.com`; then rerun the preflight and resume from the failed step. Keep completed local checks when the target SHA and relevant artifacts are unchanged. Do not claim publication after a failed push.
5. Follow the tag-triggered Release workflow for that exact tag and SHA. Confirm the Ubuntu, macOS, and Windows verification jobs, packaging, and publishing succeeded. Inspect `gh release view` for a published, non-draft Release with six binaries and the checksum file; check the remote tag target. A locally passing build or pushed tag alone is not a completed release.

Report the released version and commit, local checks, workflow result, and Release URL/assets. If any gate fails, state where the process stopped and what remains. Use the repository's current workflow and artifact naming if they have changed since this skill was written.
